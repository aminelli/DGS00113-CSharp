# Addestramento supervisionato con Random Forest in Python: esempio reale

Vediamo un esempio concreto di Machine Learning supervisionato utilizzando Random Forest, implementato in Python con `scikit-learn`.

Utilizzeremo uno scenario aziendale realistico: prevedere se un cliente abbandonerà un servizio in abbonamento (Customer Churn Prediction).

È uno dei casi d'uso più diffusi nel Machine Learning applicato al business, ad esempio nelle telecomunicazioni, nelle banche, nelle assicurazioni e nei servizi SaaS.

## 1. Scenario applicativo

Immaginiamo di lavorare per un'azienda che offre servizi di connettività Internet.

L'azienda dispone di uno storico dei propri clienti e vuole costruire un modello predittivo che identifichi i clienti con maggiore probabilità di abbandonare il servizio.

L'obiettivo è classificare ogni cliente in una delle due categorie:

- `0` = il cliente rimane.
- `1` = il cliente abbandona il servizio.

Come funziona Random Forest?

Random Forest costruisce un insieme di alberi decisionali (Decision Trees).

Ogni albero viene addestrato su un campione bootstrap del dataset e considera sottoinsiemi casuali delle caratteristiche.

Durante la classificazione, i singoli alberi esprimono una previsione e la foresta aggrega i risultati tramite voto di maggioranza.

## 4. Test e valutazione del modello

Un modello addestrato non è necessariamente un modello efficace.

Dobbiamo verificare quanto sia capace di classificare correttamente clienti che non ha mai incontrato durante l'addestramento.

### 4.1 Generazione delle previsioni

```
# Previsioni sulle osservazioni del test sety_pred = model.predict(X_test)# Probabilità di abbandonoy_proba = model.predict_proba(X_test)[:, 1]print("Prime 10 previsioni:")print(y_pred[:10])print("\nPrime 10 probabilità:")print(y_proba[:10])
```

La differenza è importante:

- `predict()` restituisce la classe prevista: 0 oppure 1.
- `predict_proba()` restituisce la probabilità stimata di appartenenza a ciascuna classe.

Ad esempio, un cliente potrebbe avere una probabilità di abbandono del 78%.

### 4.2 Valutazione attraverso le metriche

Utilizziamo le principali metriche di classificazione.

```
from sklearn.metrics import (    accuracy_score,    precision_score,    recall_score,    f1_score,    confusion_matrix,    classification_report,    roc_auc_score)print("ACCURACY:",      accuracy_score(y_test, y_pred))print("PRECISION:",      precision_score(y_test, y_pred))print("RECALL:",      recall_score(y_test, y_pred))print("F1 SCORE:",      f1_score(y_test, y_pred))print("ROC AUC:",      roc_auc_score(y_test, y_proba))print("\nCONFUSION MATRIX:")print(confusion_matrix(y_test, y_pred))print("\nCLASSIFICATION REPORT:")print(classification_report(y_test, y_pred))
```

Vediamo cosa misurano:

| Metrica   | Significato                             | Applicazione al Churn                                              |
| --------- | --------------------------------------- | ------------------------------------------------------------------ |
| Accuracy  | Percentuale di classificazioni corrette | Quanti clienti sono classificati correttamente                     |
| Precision | Affidabilità delle previsioni positive  | Quanti clienti segnalati come a rischio abbandonano davvero        |
| Recall    | Capacità di individuare i positivi      | Quanti clienti che abbandonano vengono individuati                 |
| F1 Score  | Media armonica tra Precision e Recall   | Equilibrio tra Precision e Recall                                  |
| ROC AUC   | Capacità di distinguere le due classi   | Capacità del modello di separare clienti a rischio e non a rischio |

Nel nostro scenario il Recall è particolarmente interessante: vogliamo individuare il maggior numero possibile di clienti che stanno per abbandonare il servizio.

### 4.3 Interpretazione della Confusion Matrix

La matrice di confusione consente di capire dove il modello commette errori.

Confusion Matrix – classificazione binaria

Schema concettuale, non risultati dell'esecuzione

| Realtà ↓ | Previsto: 0          | Previsto: 1          |
| -------- | -------------------- | -------------------- |
| Reale: 0 | TN<br>Vero negativo  | FP<br>Falso positivo |
| Reale: 1 | FN<br>Falso negativo | TP<br>Vero positivo  |

In particolare:

- TP (True Positive): il modello individua correttamente un cliente che abbandonerà.
- TN (True Negative): il modello individua correttamente un cliente che rimarrà.
- FP (False Positive): il modello segnala erroneamente un cliente come a rischio.
- FN (False Negative): il modello non individua un cliente che abbandonerà.

In ambito aziendale i FN possono essere particolarmente costosi: rappresentano clienti persi che l'azienda avrebbe potuto tentare di recuperare.

## 8. Ottimizzazione degli iperparametri

Finora abbiamo utilizzato valori predefiniti da noi scelti per configurare Random Forest.

In un progetto reale dobbiamo individuare la combinazione di parametri che offre le migliori prestazioni.

Possiamo utilizzare `GridSearchCV`.

```
from sklearn.model_selection import GridSearchCVparam_grid = {    "classifier__n_estimators": [100, 200, 300],    "classifier__max_depth": [8, 12, 16, None],    "classifier__min_samples_split": [2, 5, 10],    "classifier__min_samples_leaf": [1, 2, 4],    "classifier__max_features": ["sqrt", "log2"]}grid_search = GridSearchCV(    estimator=model,    param_grid=param_grid,    cv=5,    scoring="roc_auc",    n_jobs=-1,    verbose=1)grid_search.fit(X_train, y_train)print("Migliori parametri:")print(grid_search.best_params_)print("\nMigliore ROC AUC:")print(grid_search.best_score_)# Modello ottimizzatobest_model = grid_search.best_estimator_# Salvataggiojoblib.dump(    best_model,    "random_forest_churn_optimized.pkl")
```

Il prefisso `classifier__` serve perché `RandomForestClassifier` si trova all'interno della Pipeline, con il nome `classifier`.

Nota: questa ricerca può richiedere tempo, perché vengono provate numerose combinazioni di parametri. Per una valutazione rigorosa, dopo la selezione degli iperparametri è opportuno mantenere il test set completamente indipendente e utilizzarlo una sola volta per la valutazione finale.

## 11. Alcuni aspetti importanti da considerare in produzione

Il codice è completo dal punto di vista didattico, ma ci sono alcune considerazioni fondamentali per trasformarlo in un progetto aziendale:

1. Qualità dei dati: gestire valori mancanti, anomalie e duplicati.
2. Data leakage: evitare di utilizzare informazioni che non sarebbero disponibili al momento della previsione.
3. Class imbalance: verificare la distribuzione delle classi e valutare tecniche come class weighting o resampling.
4. Threshold tuning: non limitarsi alla soglia predefinita del 50%; scegliere una soglia coerente con i costi aziendali di falsi positivi e falsi negativi.
5. Monitoraggio: controllare nel tempo la qualità delle previsioni e l'eventuale cambiamento nella distribuzione dei dati.
6. Versionamento: conservare dataset, parametri, metriche e versione del modello.

Un'ulteriore precisazione: il dataset utilizzato è sintetico. Le metriche ottenute durante l'esecuzione non rappresentano quindi prestazioni dimostrate su clienti reali.
